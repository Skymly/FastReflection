# Name-based member binding without Microsoft.CSharp and the DLR: what `Type.InvokeMember`/`DefaultBinder` covers, what a custom resolver must add, and what only the runtime binder provides

Research note for GitHub issue Skymly/FastReflection#3 (feeds the binding model ticket). Date: 2026-10-24. Evidence only; no decision is made or recommended here.

## Question

Can name-based member binding — choosing a method, constructor, indexer, event or operator from a name and runtime arguments — be implemented without `Microsoft.CSharp` and the DLR? Capabilities in scope: overload resolution, named arguments, generic method type arguments, `params` and optional parameters, `null` arguments, implicit numeric conversions, static context and member paths. Compare three mechanisms — the BCL `Type.DefaultBinder`/`Type.InvokeMember`, a custom resolver, and the `Microsoft.CSharp` runtime binder — on feasibility, deviations from C# semantics, cost, and AOT/trim status on net462, netstandard2.0 and net8.0; and record what Dynamitey does for each capability.

## Short answer

Yes, binding without the DLR is implementable, and the BCL already ships a complete (if non-C#-exact) name+args binder in every TFM: `Type.InvokeMember` + `Type.DefaultBinder` + `Activator.CreateInstance`, all present since .NET Framework 1.x and in the netstandard2.0 surface. The BCL binder covers candidate enumeration by name, arity filtering, named-argument reordering, `params` expansion, optional-parameter filling (only under `BindingFlags.OptionalParamBinding`), primitive widening, `null`, ref/out write-back, static members, indexers and constructors — and accepts a custom `Binder` subclass as a plug-in point. Its semantics are a CLR widening model, not C# overload resolution: it accepts `byte→char` (explicit-only in C#), rejects all `→decimal` conversions and user-defined implicit operators, binds `null` to value-type parameters as `default(T)`, prefers longer signatures over exact-arity optional filling, and cannot bind generic methods at all — no inference and no channel for explicit type arguments. The `Microsoft.CSharp` runtime binder is a port of the C# compiler's binding pipeline and does spec-grade binding (inference, named args, optional fill, user conversions, constant narrowing, lifted operators, `IDynamicMetaObjectProvider`/COM targets); every `Binder.*` factory is `[RequiresUnreferencedCode]` on net8.0 and additionally `[RequiresDynamicCode]` from net10.0, so it runs under NativeAOT only via the expression-tree interpreter, with members prone to trimming. Dynamitey adds no binding semantics of its own — it encodes name/generic-args/named-args/static-context into `CSharpArgumentInfo`+`Binder.*` calls and caches call sites; its semantics equal the runtime binder's plus three documented patches (static properties via `get_/set_`, value-type default ctors via `Activator.CreateInstance`, event add/remove via `Binder.IsEvent`+`add_/remove_`). Everything above is verified by runtime source and a runnable probe (§5).

### 3. Per-capability detail

#### 3.1 What `InvokeMember` does before the binder sees candidates

`RuntimeType.InvokeMember` (shared CoreLib, used by CoreCLR/mono/NativeAOT) splits `BindingFlags` into the operation (`InvokeMethod`/`GetProperty`/`SetProperty`/`GetField`/`SetField`/`CreateInstance`) and the lookup mask, defaulting to `Instance|Public` (+`Static` when not creating an instance) [RT-IM L322-347]. `namedParams` may not exceed the arg count and may not contain null [RT-IM L350-361,412-413]. `binder == null` → `DefaultBinder` [RT-IM L417]. `CreateInstance` delegates to `Activator.CreateInstance(this, bindingFlags, binder, providedArgs, culture)` [RT-IM L419-427]. `""`/empty name resolves to the `[DefaultMember]` name else `"ToString"` [RT-IM L437]. Methods are collected by name via `GetMember(MemberTypes.Method)` and pre-filtered by `FilterApplyMethodBase` (visibility, static/instance, calling convention, and arity rules) [RT-IM L581-608; RT-FLT L2267-2384]; properties go through the same funnel on their get/set accessor [RT-IM L616-654]. The finalists go to `binder.BindToMethod(...)`; after `Invoke`, `binder.ReorderArgumentArray` restores caller arg order for ref/out write-back [RT-IM L672-683].

The arity pre-filter matters for optional parameters: when fewer args than parameters are supplied and `OptionalParamBinding` is **not** set, a candidate survives only if its last parameter is a `ParamArray` [RT-FLT L2324-2357]. Probe confirms: `T(1)` for `T(int,int=41)` throws `MissingMethodException` without the flag and returns `T(int,41)` with it — matching the docs ("Reflection requires `BindingFlags.OptionalParamBinding` to be specified") [IM-DOC].

#### 3.2 `DefaultBinder` semantics and observed deviations from C#

`DefaultBinder` (~1300 lines, shared across CoreCLR/Mono/NativeAOT) implements: name→position mapping (`CreateParamOrder`, exact ordinal `Equals` on `ParameterInfo.Name`; a candidate drops if any supplied name matches no parameter) [DB L1184-1228]; shortage handling that requires every unsupplied parameter except possibly the last to have `DefaultValue != DBNull.Value`, the last then being a defaulted param or a param array [DB L126-151]; excess args only into a trailing `params` array [DB L152-183]; per-argument applicability where `null` "matches with everything" (before the primitive check, so `null` also satisfies `int`/`decimal` parameters) [DB L203-212], `object` parameters match everything [DB L215-216], primitive params use `CanChangePrimitive` (the widening table), others `IsAssignableFrom` [DB L219-240]; `params`-element checking in expanded form [DB L252-279]; optional fill with `ParameterInfo.DefaultValue` and `Type.Missing` when `defaultValueBinding` (`OptionalParamBinding`) is set [DB L94,207,244,336-344]; and a "most specific" walk (`FindMostSpecificMethod` → `FindMostSpecific`/`FindMostSpecificType`): params-using members lose to non-params ("A method using params is always less specific") [DB L868-870], equal-parameter signatures resolve by declaring-type depth [DB L1027-1046], and when nothing distinguishes two candidates by parameter types the *longer* parameter list wins [DB L921-931]. Ambiguity or no match → `AmbiguousMatchException`/`MissingMethodException` [DB L296,388-389]. `ChangeType` throws `NotSupportedException` — "the default binder doesn't support any change type functionality"; the actual argument coercion is in invoke-time `CheckValue`/`TryChangeTypeSpecial` (primitive widening, "Enum treated as underlying type", `null`→`default(T)` for value types, rebox to `Nullable<T>`) [DB L750-753; RT-CV L791-978]. `SelectMethod`/`SelectProperty` back `Type.GetMethod(name, Type[])`-style lookup — exact-or-widening match on a `Type[]` signature only (no names/nulls/optional/params) [DB L540-630,633-745]. The public extension point exists: docs say to pass a `Binder`-derived instance via `InvokeMember`'s `binder` parameter when different rules are needed [DB-T].

Observed deviations from C# §12.6.4/§10.2.3 (probe §5, identical on .NET 8.0.32 and .NET Framework 4.8 — only exception text is localized):

- `byte→char` **accepted** (C#: explicit-only [SPEC §10.2.3/§10.3.2]); the doc's own conversion table lists `Byte→Char` [DB-T].
- `int→decimal` **rejected** — the widening table has no `→decimal` targets at all [DB L1244-1264]; C# lists `int→decimal` implicit [SPEC §10.2.3]. Same for `char→decimal`, `sbyte→decimal`, etc.
- Constant narrowing **unsupported** — boxed `5` fails `ByteOnly(byte)`; C# allows range-checked constant conversions [SPEC §10.2.x]; the runtime binder honors it via `CSharpArgumentInfoFlags.Constant` (probe `dynamic ByteOnly(5)` works, `R(0)`→enum works) [CAI].
- `int`→enum **rejected** (C# also rejects except literal `0`; the binder rejects `0` too since it sees only runtime types) — probe `R(1)` `MissingMethodException`, dynamic `R(0)` ok.
- User-defined `implicit operator` **not consulted** (probe `U(new Bar())` → `MissingMethodException`); C# searches them [SPEC §10.2].
- `null` binds to value-type parameters as `default(T)` (probe `Q(null)` → `Q(decimal)` ran with `0m`), and `null` applicability makes `M(null)` ambiguous across `{int,long,object,string,sb}`; C# rejects `null`→non-nullable value type outright and reports ambiguity between the top ref-type candidates only (`dynamic M(null)` → "ambiguous between M(string) and M(StringBuilderDummy)", spec-correct).
- With `OptionalParamBinding`, `T1(1)` against `T1(int)`+`T1(int,int=42)` picks the **longer** `T1(int,int=42)` [DB L921-931]; C# prefers the member needing no default substitution [SPEC §12.6.4.3] — `dynamic T1(1)` picks `T1(int)`. Same for ctors: `new CtorProbe(5)` + flag picks `CtorProbe(int,int)` filling `y=7`.
- No generic methods: no `typeArguments` parameter exists on `InvokeMember`, no inference runs, and open `G<T>` params fail the assignability checks (probe `G<T>(5)` → `MissingMethodException`).
- No events: no `BindingFlags` operation addresses them (probe `InvokeMember("Evt", InvokeMethod)` → `MissingMethodException`).
- No member paths: `"Field.ToString"` → `MissingMethodException`; `""` maps to the `[DefaultMember]` (`Item`) then fails as a method.

Non-deviating coverage confirmed by probe: exact/overloaded matches, `short`/`byte`→`int` widening, `int`→`long`, `int`→`int?` (`Nullable<T>` assignability), named-arg reorder and partial named+optional fill, `params` normal/expanded incl. normal-form preference, static members, `Item[int]` vs `Item[long]` indexer overloads (`Item[null]` picks `int`), 1-param vs optional-2-param ctor without the flag, `op_Addition` by metadata name as a static method, `NonPublic` methods, `GetField`/`SetField`, ref/out write-back (`y=5,z=4`).

#### 3.3 What the `Microsoft.CSharp` runtime binder actually is

The `Binder.*` factories create `CallSiteBinder` subclasses; binding defers through DLR `Fallback*` into `RuntimeBinder`, whose `Semantics` subtree is a port of the C# compiler's binding pipeline — `MemberLookup`/`MemberLookupResults`/`CMethodIterator` (member lookup over a name, restricted to the receiver's containing types and their bases [RB-MI L53,L152-165; RB-MLR L30-32]), `GroupToArgsBinder` (the §12.6.4 loop: iterate candidates, build expanded params form on demand, reorder named args, add optional args, infer type args, track inaccessible/misnamed/bogus results) [GB L114-200], `DetermineCurrentTypeArgs` → `MethodTypeInferrer.Infer` (~1700-line port of §12.6.3 two-phase inference; explicit type args skip inference — "Can't infer if some type args are specified") [GB L858-903], `ReOrderArgsForNamedArguments`/`AddArgumentsForOptionalParameters` (incl. a `DateTime` default-value special case) [GB L368,501-560], `ConstructExpandedParameters` (called at L132, defined L819), and the `Conversion`/`ImplicitConversion`/`ExplicitConversion`/`Conversions` engine including user-defined operators [RB-CONV]. Per-argument metadata arrives as `CSharpArgumentInfo` flags — `UseCompileTimeType`, `Constant`, `NamedArgument`, `IsRef`, `IsOut`, `IsStaticType` [CAI]. Accessibility is C#-real: `SemanticChecker.CheckAccessCore` enforces private/protected/internal against the `context` (`AggregateSymbol` of the calling context type) [RB L24-41; SC L117-195]; probe of Dynamitey's own tests shows private methods are reachable when context = declaring type and rejected when context is a foreign type [DY-PT L28-65]. A null receiver for a non-static call throws `NullReferenceOnMemberException` [RB L699-703]. Static calls need `IsStaticType` and make the target `ExprClass` [RB L690-696] — but there is no name lookup for `get_X` on a static class path, hence Dynamitey's `get_/set_` rewrite [DYH L452-538]. Extension methods are not searched (`CMethodIterator` only iterates containing types; probe `d.Ext()` fails on both net8.0 and net472 — matching the long-documented "extension methods cannot be dynamically dispatched" limitation). `IDynamicMetaObjectProvider` targets bind themselves first via the DLR fallback protocol [CIM L111-135]; COM is delegated to `ComInterop`/`ComBinder` on builds with `ENABLECOMBINDER` [CIM L122-129]. Result-discard calls need `CSharpBinderFlags.ResultDiscarded` (why Dynamitey splits `InvokeMember`/`InvokeMemberAction`) [DYH L675]. Every layer is `[RequiresUnreferencedCode]` — 30+ sites in `RuntimeBinder.cs` alone [RB L24…1285].

#### 3.4 What Dynamitey adds on top of the runtime binder (per capability)

Dynamitey contributes no binding semantics; it marshals names/flags into `Binder.*` and caches `CallSite`s by a `BinderHash` key (member name + context + arg names + binder type + flags) [DYH L341-375]. Concretely:

- Name + generic type args: `InvokeMemberName(name, Type[])` → `Binder.InvokeMember(flags, name.Name, name.GenericArgs, context, args)`; `IsSpecialName` → `CSharpBinderFlags.InvokeSpecialName` [DYN-IMN L79-95; DYH L584-594].
- Named args: `InvokeArg(name,value)` unwrapped into a `string[] argNames` then `CSharpArgumentInfoFlags.NamedArgument` [DYN-IA L29-70; UTIL L176-211; DYH L211-249].
- Static context: `StaticContext(Type)`/`InvokeContext` mark the target `Type` and set `IsStaticType|UseCompileTimeType` on arg0; context type defaults to the target's runtime type, so private members of that type are reachable — overridable via `InvokeContext.CreateContext(target, context)`/`CacheableInvocation(context:…)` [IC L30-49,54-109; UTIL L97-112; DY-PT L28-65].
- Static properties: rewritten to `get_`/`set_` + `IsStaticType` because "CSharp Binder won't call Static properties, grrr" [DYH L452-538].
- Events: `Binder.IsEvent` probe then `add_`/`remove_` special-name call, else get/`+=`/set fallback for delegate-valued members [DYH L717-762; DYN L620-669].
- Constructors: `Binder.InvokeConstructor`; value type + 0 args → `Activator.CreateInstance` because "dynamic invocation doesn't see no argument constructors of value types" [DYH L796-825; DYN L926-938].
- Indexers: `Binder.GetIndex`/`SetIndex` [DYH L623-661; DYN L342-383].
- Member paths: `InvokeGetChain`/`InvokeSetChain` — regex `((\.?(?<Getter>\w+))|(\[(?<IntIndexer>\d+)\])|(\['(?<StringIndexer>\w+)'\]))` then sequential `InvokeGet`/`InvokeGetIndex` [DYN L577-608,472+].
- Conversions: `InvokeConvert` → `Binder.Convert`; `CoerceConvert` adds a fallback ladder (delegate coercion → `ActLike` → explicit convert → `Enum.Parse` → `Convert.ChangeType` → `TypeConverter`) [DYN L679-686,814-918].
- Operators: `InvokeBinaryOperator`/`InvokeUnaryOperator` are `dynamic` expressions — i.e., the runtime binder's operator machinery incl. lifted/predefined [DYN L216-318].
- Methods that return `void` need `InvokeMemberAction` (`ResultDiscarded` flag) [DYN L408-416].
- Arity beyond the T4-pre-generated delegate signatures requires `ImpromptuInterface`'s `EmitCallSiteFuncType` (runtime type emit; `TypeLoadException` without it) [DYH L87-107].
- Known self-reported defects (from landscape §2.3): `BinderCache` uses plain `Dictionary` (author-reported corruption under concurrency, issue #50); first call per site pays full C#-semantics + expression compile.

#### 3.5 AOT/trim status on net8.0

- **BCL binder**: no `[RequiresUnreferencedCode]`/`[RequiresDynamicCode]` on `InvokeMember`/`BindToMethod`; the obstacle is dataflow — `InvokeMember` is `[DynamicallyAccessedMembers(All)]` on `this`, so calling it on an unannotated `Type` warns IL2075 and the target members must be rooted at publish [IM; IL2075]. `DefaultBinder`'s `params`-array construction is IL3050-suppressed with the justification "AOT compiler ensures params arrays are created for reflection-invokable methods" — i.e., intended to keep working under NativeAOT [DB L29-30]. Behavior is identical on net8.0 and .NET Framework 4.8 (probe §5).
- **Custom resolver**: identical dataflow story for member enumeration (`GetMethods`/`GetProperties`/`GetEvents` are `DynamicallyAccessedMembers`-annotated per kind); the selection logic itself is pure metadata — no dynamic code required anywhere. AOT-compatible by construction if it avoids emit for *binding* (the emit/compiled-delegate question is orthogonal — invocation is a separate stage).
- **`Microsoft.CSharp` runtime binder**: IL2026 on every public `Binder.*` factory and ~130 internals sites on net8.0/net9.0 [RB-F L19 ff]; net10.0 adds `[RequiresDynamicCode("The 'dynamic' feature requires runtime-code generation, which is incompatible with AOT.")]` on the same surface (PR #114346 — "the public API surface looks exactly like RequiresUnreferencedCode") [PR114346; RB-F10 L20,L31-32]. Under NativeAOT it still *executes*: `LambdaExpression.Compile()` falls back to the `LightCompiler` interpreter when `RuntimeFeature.IsDynamicCodeSupported == false` [SLE L29,L137-150] — Microsoft: "The expression trees interpreter works today... use of expression trees will generate AOT compatibility warnings and our recommendation is going to be to avoid them for good results" [ISS61231]; and interpreted expressions "increas[e] app size" and are slower than plain reflection per dotnet/runtime#81258 [ISS81258]. The trimming failure mode is exactly the warning text: binder lookups happen by name over runtime types, so trimmed members fail at runtime with `RuntimeBinderException` rather than a bind-time signal.
- **Dynamitey**: same DLR annotations, plus `CallSite<T>` delegate-type construction (`Func`/`Action` arities, `MakeGenericType`) and the optional ImpromptuInterface emit tail [DYH L84-107]. On netstandard2.0 it additionally forces the `Microsoft.CSharp` NuGet package on consumers; on net40/net462 the framework assembly is free [DY-PRJ].

#### 3.6 What only the DLR route provides

From the evidence above, the capabilities that have no BCL-binder path and would cost real work in a custom resolver: C#-exact conversions (full implicit/explicit set incl. user-defined ops, `Constant`-flag narrowing, lifted operators), method type inference (the ~1700-line `MethodTypeInferrer` port of §12.6.3), `IDynamicMetaObjectProvider`/`DynamicObject` targets, COM interop binding, and the three-level call-site polymorphic cache (per-runtime-type inline caching). The capabilities a custom resolver gains over the BCL binder cheaply: spec-correct widening table, `null` handling restricted to nullable targets, correct optional-parameter tie-break, generic methods via explicit type args (inference optional), events via `EventInfo`, member-path splitting, case option, and a TryBind-style error model — all on a metadata-only path with no codegen requirement.

// dynamic (runtime binder):

d.Q(1)              // -> "Q(decimal)"

## Caveats and unknowns

- Probe: one machine, Windows x64, .NET 8.0.32 + .NET Framework 4.8.10008.0. Not exercised: NativeAOT/trimmed publish end-to-end (annotation evidence is source-level), Mono, `params`+named-arg-for-array edge cases, `in`/`ref readonly` params through either binder, `ref struct`/`Span` parameters, `BindingFlags.FlattenHierarchy`/`Inherited`/`DeclaredOnly` nuances, `SelectMethod` via `GetMethod(name, types)`, late-bound `Invoke` on delegates, and the `OleAutBinder.ChangeType` path used by `ForwardCallToInvokeMember` (not the `InvokeMember` path) [RTC L4119-4120].
- The runtime binder is a port of the C# 4-era compiler binder; C# features added since (e.g. `in` modifiers, newer betterness rules) may deviate — not audited rule-by-rule; the probe confirms the headline cases.
- "Cost" figures for a custom resolver are estimates from the DefaultBinder (~1300 lines) and `MethodTypeInferrer` (~1700 lines) sizes, not a measured build.
- Dynamitey findings are from source at `c44f5c5` (3.0.3-era HEAD) + its tests; the Dynamitey.Community fork was not re-inspected.
- Whether `Microsoft.CSharp`'s `Binder.*` methods are usable *without warnings* in an `IsTrimmable` net8.0 library: they cannot be — IL2026 is unconditional on the API surface; consuming them requires `[RequiresUnreferencedCode]` propagation or `UnconditionalSuppressMessage`.
- `Type.InvokeMember` under mono/netstandard2.0-on-Framework was assumed identical by shared-source inspection, not run.

## Implications for the decision ticket

- Three binding routes exist on all three TFMs; none is eliminable by availability alone. The BCL binder is free and AOT-safe but semantically frozen and non-extensible in place (it can only be *replaced* via the `Binder` parameter, not configured).
- Where C#-exactness matters (user-defined conversions, generic inference, correct `null`/optional/params semantics per spec), the evidence supports only two suppliers: a hand-rolled resolver, or the `Microsoft.CSharp` runtime binder with its IL2026/IL3050 surface and interpreted-expression execution under NativeAOT.
- Where binding semantics need only be "reasonable" (documented widening, named/optional/params, ambiguity diagnostics), DefaultBinder already covers them with stable cross-runtime behavior — its deviations are enumerable and testable (probe list in §3.2).
- Dynamitey's layering shows the DLR tax buys C# semantics plus three required patches (static props, value-type ctors, event add/remove) — a custom resolver would need those same patches against `Type.GetEvents`/indexer metadata instead, plus whatever it chooses for extension methods and `IDynamicMetaObjectProvider`.
- The `Binder`-subclass plug-in (`InvokeMember`'s `binder` parameter + `ReorderArgumentArray` state contract) is a formally supported hybrid: keep `InvokeMember`'s plumbing, replace only `BindToMethod`/`SelectMethod`/`SelectProperty`/`BindToField`/`ChangeType` semantics.
